## Policy formulations

All final policies operate over the same prepared target station-hour rows for a given transfer direction. The outcome captured is a target recorder-positive hour occurring while `on`; capture is `sum(on * recorder_detected) / sum(recorder_detected)` (station_results.py:80-82, 177-184).

| Policy | Inputs and history | Decision | Training/configuration |
|---|---|---|---|
| Fixed schedule (no adaptation) | Source recorder labels by calendar `month × hour`; fallback source hour mean if a source cell is absent (station_results.py:150-156). No target history, camera feature, or target labels. | Record every target hour whose source `month × hour` rate is at least a source-tuned cutoff (lines 157-161). Cutoff is the rate at which source positive hours cumulatively reach 80% after sorting source rows by rate. | Source-only, rule/table based; not a learned model. |
| Random schedule / equal-budget baseline | Final result does **not** simulate a sequence of random draws. It uses the expectation that random independent target hours capture the same percentage as recorder-on budget (station_results.py:229-235). | Reported capture = adaptive `% on`; recorder hours and bootstrap `% on` copied from adaptive. | Analytical expected-value baseline, not a fitted policy. The adaptive simulator’s 10% random audit is different from this baseline. |
| Adaptive with camera tip-off | Per station: borrowed source hourly prior; labels only from prior hours that this target station was actually switched on; hours/dates for age weighting; current and prior sampled-night camera flags; seed for 10% audit (adaptive_schedule.py:66-94). | At each hour: calculate decayed posterior-like rate, turn on if rate ≥ threshold **or** prior/current-night camera cue **or** random audit draw <10% (lines 75-91). ### Camera timing and label use

**[Code verified]** The adaptive policy receives the *current hour’s* camera label only after making that hour’s audio decision: the `if r.camera_detected` update follows `recorded[pos] = on` (adaptive_schedule.py:84-92). It can use an earlier camera detection within the same ordered night and `prev_night_camera` from the immediately preceding *sampled* night (lines 71-73, 83, 93). Camera is otherwise assumed available/free in this offline simulation; no camera latency, false positive, false negative, or cost model is implemented.

**[Code verified]** Recorder labels (`r.recorder_detected`) are appended only when audio is on (adaptive_schedule.py:86-91). Thus target recorder outcomes do influence subsequent target decisions, but only for selected/audited hours; no unrecorded target label is used to update. Fixed and random expected baselines do not update on target observations. The oracle does use target labels by definition.

## Online adaptation reconstructed

For each target station, `transfer()` makes `prior_from_src = {station: hourly_mean(source)}` (station_results.py:191-195). `hourly_mean` is the source mean recorder detection rate by hour, reindexed to the 14-hour night order and fills absent hours with 0.05 (lines 76-78). This is one shared hourly source prior repeated for all target stations; it is not a fitted cross-river classifier and does not condition on month, station type, or camera.

On each target sampled night, the policy recomputes for each hour (h):

`rate(h) = (3 × prior(h) + Σ[w_i × y_i]) / (3 + Σ[w_i])`

where (i) ranges over earlier **recorded** target observations at that station and hour, (y_i) is recorder detection, and `w_i = 0.5 ** (age_days / 30)` (adaptive_schedule.py:75-86). “Worth 3 nights” is therefore a pseudo-weight of 3 in the denominator/numerator, not three initial labelled target nights. **[Code verified]** The first three nights are not automatically recorded or treated as labelled: only threshold/camera/audit-selected hours enter the history.

* **Zero-shot / frozen transfer:** **[Unknown]** No named adaptive “prior only, zero target updates” variant exists. **[Code verified]** Fixed scheduling is source-only and frozen, but adaptive has no switch that prevents selected recorder outcomes being appended (or that adds an update cutoff).
* **First 1 night then frozen:** **[Unknown]** No named first-night frozen variant exists. **[Code verified]** No code limits `obs_*` history to a first-night period.
* **First 3 nights then frozen:** **[Unknown]** No named first-three-night frozen variant exists. **[Code verified]** `START_NIGHTS=3` is a prior weight, not an update limit; no freeze-after-three-nights switch exists.
* **Unlimited nightly updating:** **[Code verified]** The existing `run_station()` continually retains all selected past observations, with exponential temporal downweighting, on every sampled night (adaptive_schedule.py:70-93).

## Evaluation and bootstrap

**Budgets and equal eligibility.** Each policy’s budget is average `on` over all target eligible station-hours. `load()` has already removed rows missing either sensor, so the evaluated dataset is common across policies (load.py:21-25). Fixed and adaptive can choose different subsets of those same hours; random is an expectation matched to adaptive’s realized mean budget. It is not an hour-by-hour matched random sample.

**Source tuning.** Fixed cutoff is selected from source only (station_results.py:157-161). Adaptive threshold considers each grid value and selects the largest meeting ≥80% source capture under leave-one-station-out source priors (station_results.py:164-174). The selected cutoff/threshold is frozen for target evaluation, but adaptive target label updates continue online; therefore “frozen” applies to the setting, not all target-state adaptation.

**Oracle and capture.** Oracle’s budget is target prevalence of recorder positive hours and capture is 100% (station_results.py:222-227). Final evaluation is recorder-positive capture, not system-level camera+audio detection. The older `energy.py` has a conversion function, but final station outputs do not call it and report no operating-cost calculation (energy.py:9-20; station_results.py:335-359). The appropriate final cost proxy is recorder-on station-hours / `% on`.

**Station bootstrap for single-policy estimates.** `boot_ratio()` aggregates numerator and denominator to station, resamples station indices with replacement to an array of shape 2,000 × number of stations under `default_rng(0)`, then reports 2.5th and 97.5th percentiles (station_results.py:44-54). This resamples whole station totals, not hours/nights; it is a ratio of resampled sums. The calls made for on share and caught share are separate but deterministically use seed 0, hence draw-index paired in practice (station_results.py:177-184).

**Equal-budget paired bootstrap.** For every target station, adaptive is evaluated at every threshold and fixed at every source-derived cutoff (equal_budget_ci.py:25-35). One resampled station-weight vector is applied to both policy curves, each is pooled, sorted by `% on`, made nondecreasing in capture, and linearly interpolated at 20/30/40/60% budgets without extrapolation (lines 39-45, 53-64). The same draw therefore gives an adaptive-minus-fixed paired difference. It uses seed 0 once before target loops; the random-number stream then continues into the second target (lines 53-62). Values outside an available curve are NaN and omitted by `nanpercentile`; output reports the fraction of resamples reaching the budget (lines 64-73). The report removes the misleading 20% rows from prose because the adaptive curve’s minimum is about 23–29% (station_results.md:65-69), although the CSV retains them.

## Camera tip-off reliability

**[Code verified]** The only implementation is binary perfect availability: `if r.camera_detected: camera_cue = True`; the no-tip-off comparison overwrites all camera values with zero (adaptive_schedule.py:91-93; station_results.py:188-203). Thus the existing code supports the two endpoints 100% (observed camera positive always cues) and 0% (no tip-offs), but does **not** support reproducible 75% or 50% reliability experiments.

To test 75%/50%, a change would be required before/inside `run_station()` to stochastically retain or suppress camera positives with a specified, seeded sensitivity model. The choice must specify whether reliability means false negatives only, whether it acts per detection/hour/night, and how it is seeded. No false-positive model exists. This is a required clarification, not an implemented result.

## Known assumptions and limitations

* **[Code verified]** The simulation evaluates 10-minute recorder presence within a sampled hour as if the policy decision controls that station-hour; it cannot evaluate continuous audio coverage (config.py:26-30).
* **[Code verified]** Source/target “river systems” are also different campaigns/years; Kaoping station grouping is inferred (clean_grassowl.py:19-22; data dictionary:38-44).
* **[Report stated]** Camera is treated as always on and cheap; camera operating cost was not measured (station_results.md:104-113).
* **[Report stated]** Labels may be noisy and owl-call identification is unpublished (station_results.md:106-109).
* **[Code verified]** Breeding status is descriptive only, not an adaptive input (adaptive_schedule.py:66-94; station_results.py:123-145).
* **[Code verified]** There is no learned ML classifier in the final station transfer pipeline; “adaptive” denotes a hand-specified decayed hourly-rate rule.
